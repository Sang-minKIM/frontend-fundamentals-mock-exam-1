# Frontend Fundamentals 모의고사

## Getting started

```sh
yarn dev
```

## 구현을 위해 추가한 라이브러리

- `@tanstack/react-query`: 서버 상태 관리 (Suspense 사용)
- `react-hook-form`: 폼 상태 관리 및 validation
- `zod`: 스키마 기반 폼 validation 정의, 런타임 타입 검증
- `@hookform/resolvers`: react-hook-form과 zod 연동
- `suspensive`: Errorboundary 설정, Delay로 짧은 로딩 시간인 경우 로딩 화면을 보여주지 않고 컴포넌트 노출 시점 조절

## 프로젝트 구조

```
src/
├── pages/
│   ├── savingsCalculator/       # 페이지 컴포넌트들을 도메인별로 구성
│   │   ├── components/          # savingsCalculator 하위 컴포넌트
│   │   ├── queries/             # 서버 상태 관리 레이어. queryKey, endpoint, queryOption, response schema 포함
│   │   ├── services/            # 비즈니스 로직 레이어. 순수 함수 형태로 구현된 계산, 필터링, 변환 등의 도메인 로직
│   │   └── types/               # 타입 정의. 폼 상태 타입 등 클라이언트 상태의 타입
│   └── Routes.tsx
├── providers/                   # 전역 provider
└── utils/                       # 유틸리티 함수
```

> **참고**: 비즈니스 로직을 React Hook 형태로 구현해야 하는 경우에는 `hooks/` 폴더를 사용합니다. 현재 프로젝트에서는 순수 함수 형태로 충분하므로 `services/` 폴더를 사용했습니다.

## 요구사항 분석 및 가설

### 입력 필드 Validation 및 계산 결과 탭 접근 제어

**요구사항 분석:**

- 계산 결과는 선택한 상품이 필요함
- 추천 상품 목록은 입력 조건만 필요함
- 계산 결과 탭 클릭 시 `CalculationResult` 컴포넌트 표시

**가설:**

1. **탭 전환 제어**
   - 탭은 자유롭게 이동 가능하도록 구현
   - Validation 체크로 탭 전환을 막지 않음
   - 사용자가 언제든지 계산 결과를 확인할 수 있도록 함

2. **실시간 계산 결과 표시**
   - 입력값 변경 시 즉시 계산 결과 업데이트 (따로 계산 버튼이 존재하지 않음)
   - 입력값이 없으면 0으로 계산하여 표시
   - 선택한 상품이 없으면 "상품을 선택해주세요" 메시지 표시
   - 선택한 상품이 있으면 입력값이 0이어도 계산 결과 표시

3. **Validation 규칙**
   - Zod 스키마 기반 form-level validation 적용
   - 각 필드별 에러 메시지는 해당 필드 아래에 표시
   - 금액 필드는 숫자 형식 및 양수 검증
   - 저축 기간은 6, 12, 24개월 중 선택

### API 로딩 상태 처리

**요구사항 분석:**

- React Query + Suspense 사용
- 추천 상품 목록은 입력 조건만 필요
- 계산 결과는 선택한 상품 필요

**가설:**

1. **추천 상품 목록 처리**
   - API 로딩 중이면 추천 상품 목록 섹션을 아예 렌더링하지 않음
   - 추천 상품은 선택사항이므로 로딩 상태를 보여줄 필요 없을거라 판단

2. **계산 결과 처리**
   - 계산 결과는 선택한 상품이 있을 때만 표시
   - API 로딩 상태와 무관하게 선택 상품이라는 클라이언트 상태 기반으로 처리 (API 로딩이 안되었다면 선택 상품도 없겠지만)

### 저축 목표 필터링

- 저축 기간은 기본값이 있고 선택이기 때문에 항상 존재
- 월 납입액은 입력을 해야 존재함. 그래서 입력을 안했을 때에는 필터링 안함

## 추상화 및 설계 고민

### 상태 관리 전략

**고민 사항:**

- 선택한 적금 상품을 form 상태에 포함할지, 별도 상태로 관리할지

**결론:**

- 선택한 적금 상품을 form 상태에 포함하기로 결정

**판단 기준:**

1. **사용 목적**
   - 계산 결과: 선택한 적금 상품 필요
   - 추천 상품 목록: 입력 조건만으로 계산 가능
   - **이것만으로는 form 상태 포함 여부 결정 어려움**

2. **폼 응집도 ([Frontend-Fundamentals - 폼의 응집도 생각하기 기반](https://frontend-fundamentals.com/code-quality/code/examples/form-fields.html)**
   - 적금 상품 목록이 입력 조건에 따라 필터링 -> 선택 상품 초기화 필요
   - **연관된 상태기 때문에 폼 전체 단위 응집도가 적절함**
   - 폼 전체 단위 응집도를 선택

3. **컴포넌트 구조상 폼의 범위**
   - 요구사항을 분석 해보았을 때 HTML form은 사용할 필요 없음 (form상태 기반 즉시 계산되는 형태)
   - FormProvider로 상태 공유 범위가 적절한지 생각해봄
     - 입력 필드들 (form 상태 쓰기)
     - 적금 상품 탭 (form 상태 읽기) -> 선택 상품 포함 한다면 form 상태 쓰기 추가
     - 계산 결과 탭 (form 상태 읽기)
   - 선택 상품을 form에 포함해도 상태 공유 범위 똑같음

4. **Validation**
   - 계산 결과 탭에서 "상품을 선택해주세요" 메시지 표시
   - **form 상태에 선택 적금 상품 포함하는 경우 form validation으로 처리 가능**

5. **추후 입력 조건 초기화와 같은 기능이 추가된다면?**
   - **form 상태에 선택한 적금 상품을 포함하는 경우 form.reset으로 관리 가능**

### 컴포넌트 구조 설계

**고민 사항:**

1. **필드 컴포넌트 추상화**
   - 폼 필드 입력 로직을 각 필드별로 분리할지, 모든 폼 필드를 하나로 분리할지 고민
   - 필드별로 입력 로직을 책임지는 컴포넌트로 분리
   - 레이아웃을 상위에서 책임지게 하고 싶었고 각 필드 입력 로직을 하나의 컴포넌트에서 담당하게 하기 위함

2. **계산 결과 컴포넌트 추상화**
   - 각 계산 결과(예상 수익 금액, 목표 금액과의 차이, 추천 월 납입 금액)를 별도 컴포넌트로 분리
   - 필드 컴포넌트를 추상화 했던 것과 동일한 이유로 추상화

3. **SuspenseQuery 사용**
   - 데이터 fetching 로직은 사용하는 쪽(`SavingsCalculatorPage`)에서 드러나게 함
   - 어떤 컴포넌트가 suspenseQuery를 사용하는지를 상위에 드러나게 하기 위함
   - 컴포넌트는 순수하게 렌더링만 담당하도록 설계

4. **ListHeader의 위치**
   - `ListHeader`는 리스트의 헤더이므로 리스트 컴포넌트 내부에 유지
   - 헤더와 리스트 사이의 `Spacing`도 리스트의 일부로 함께 관리
   - 응집도 높이기 원칙에 따라 관련 코드를 함께 유지
